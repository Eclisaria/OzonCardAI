# Правила разработки OzonCardAI для Codex

## Общие правила

- Никогда не ломать существующую архитектуру проекта.
- Не переписывать работающий код без необходимости.
- Не изменять файлы, не относящиеся к текущей задаче.
- Не создавать дублирование классов, функций и модулей.
- Не писать несколько реализаций одного и того же функционала.
- Использовать существующие компоненты и расширять их, если это возможно.
- Использовать существующий стиль приложения и не создавать параллельную систему оформления.
- Использовать современный Python 3.12+.
- Следовать PEP8 и поддерживать читаемую структуру кода.
- Разделять UI и бизнес-логику.
- Не писать большие монолитные файлы.
- Не добавлять сторонние библиотеки без явной необходимости.
- Не реализовывать внешние интеграции раньше соответствующего этапа roadmap.

## Правила архитектуры

- `main.py` должен оставаться легкой точкой входа и только запускать приложение.
- `app/ui/main_window.py` должен отвечать за главное окно, компоновку и переключение страниц.
- Страницы интерфейса должны развиваться в отдельных UI-модулях, а не превращать главное окно в монолит.
- QSS-стили должны храниться отдельно от логики интерфейса.
- API-клиенты должны находиться в `app/api/`.
- Бизнес-сценарии должны находиться в `app/services/`.
- Доменные модели должны находиться в `app/models/`.
- Долгие операции в будущем должны выноситься в `app/workers/`.

## Правила Git

- Категорически запрещено оставлять в проекте маркеры merge-конфликтов Git.
- Запрещенные маркеры включают строку из семи символов «меньше», строку из семи знаков равенства и строку из семи символов «больше».
- После завершения работы подобных строк не должно существовать ни в одном файле проекта.
- Если возникает merge-конфликт, необходимо самостоятельно разрешить его до финального ответа.
- Оставлять только одну итоговую реализацию.
- Не использовать устаревшие версии файлов при разрешении конфликтов.
- Не откатывать проект к предыдущему состоянию без прямого указания пользователя.
- Не заменять новую архитектуру старой.
- Не создавать изменения, которые ломают `git pull`, `git merge` или `git rebase`.
- Не создавать код, который провоцирует конфликты GitHub.
- Не оставлять временные решения.
- Не оставлять закомментированный старый код.
- Перед завершением работы обязательно проверить проект на отсутствие merge-конфликтов.

## Правила качества кода

- Код должен быть простым, понятным и расширяемым.
- Имена классов, функций и переменных должны отражать назначение.
- Комментарии добавлять только там, где они действительно объясняют неочевидное решение.
- Не смешивать сетевую логику, бизнес-логику и UI.
- Не блокировать UI долгими операциями.
- Не добавлять заглушки, которые выглядят как рабочая интеграция.
- Не хранить токены, секреты и персональные данные в репозитории.

## Проверки перед завершением

- Проверить статус Git.
- Проверить отсутствие merge-конфликтов.
- Проверить синтаксис Python-файлов.
- Проверить запуск приложения командой `python3 main.py`, если окружение содержит все зависимости.
- Убедиться, что изменены только файлы, относящиеся к текущей задаче.
