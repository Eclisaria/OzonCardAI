# Workflow разработки OzonCardAI

## 1. Изучить текущую архитектуру

Перед внесением изменений необходимо понять существующую структуру проекта:

- посмотреть текущий статус Git;
- изучить дерево файлов без использования медленных рекурсивных команд;
- открыть релевантные модули;
- определить, какие файлы действительно относятся к задаче.

## 2. Понять задачу

Перед реализацией нужно зафиксировать:

- какой слой приложения затрагивается;
- относится ли задача к UI, сервисам, API, моделям, документации или инфраструктуре;
- какие ограничения указаны пользователем;
- какие части проекта нельзя менять.

## 3. Изменять только необходимые файлы

При выполнении задачи необходимо:

- не менять функциональный код, если задача касается только документации;
- не менять документацию, если задача касается только кода, кроме случаев, когда это явно требуется;
- не форматировать весь проект без необходимости;
- не переименовывать существующие файлы без причины;
- не удалять рабочие компоненты.

## 4. Сохранять существующий функционал

Любое изменение должно быть совместимо с текущей архитектурой:

- главное окно должно оставаться на `QMainWindow`;
- навигация должна продолжать переключать страницы;
- меню, toolbar и status bar должны оставаться рабочими;
- стили должны применяться централизованно;
- точка входа должна оставаться простой.

## 5. Проверить код после изменений

После написания кода необходимо проверить:

- корректность импортов;
- синтаксис Python-файлов;
- отсутствие неиспользуемого кода там, где это можно заметить без дополнительных инструментов;
- отсутствие случайных изменений в нерелевантных файлах;
- отсутствие merge-конфликтов Git;
- отсутствие временных или закомментированных старых реализаций.

## 6. Проверить запуск приложения

Если окружение содержит зависимости, нужно запустить:

```bash
python3 main.py
```

Если приложение запускается в headless-среде, можно использовать offscreen-платформу Qt:

```bash
QT_QPA_PLATFORM=offscreen timeout 3 python3 main.py
```

Если зависимость PyQt6 отсутствует или установка невозможна из-за ограничений окружения, это нужно явно указать в финальном отчете.

## 7. Проверить Git перед завершением

Перед финальным ответом необходимо выполнить проверки:

- убедиться, что нет лишних файлов;
- убедиться, что нет маркеров merge-конфликтов;
- проверить `git status`;
- закоммитить только релевантные изменения;
- подготовить PR-описание, если были внесены изменения.

## 8. Финальный отчет

В финальном сообщении нужно указать:

- краткое резюме изменений;
- какие файлы были изменены;
- какие проверки запускались;
- какие проверки не удалось выполнить из-за ограничений окружения;
- хеш коммита, если был создан коммит.
